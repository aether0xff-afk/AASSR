# AASSR 위키 문체 안내

이 페이지는 AASSR 위키에 새 문서를 쓰거나 기존 문서를 수정할 때 사용하는 **독자 기준과 문체 규칙**을 설명한다.

AASSR 위키의 기본 독자는 강화학습 전공자가 아니다.

주요 독자는:

- 인공지능을 독학하는 학생
- 연구를 처음 시작한 학생 연구자
- 관련 전공은 아니지만 직접 구현하는 아마추어 개발자
- 개인 프로젝트로 강화학습을 실험하는 연구자
- AASSR 코드를 처음 보는 외부 개발자

이다.

---

# 1. 가장 중요한 원칙

> **전문용어를 없애지 말고, 전문용어를 몰라도 그 문장을 먼저 이해할 수 있게 쓴다.**

좋지 않은 예:

```text
OOD에서 local support가 낮으면 Critic override를 fail-closed gate로 막는다.
```

권장 예:

```text
학습 때 충분히 보지 못한 영역(OOD)에서는
미래 가치 평가를 뒷받침하는 실제 학습 경험이 부족할 수 있다.
이때는 근거 없는 높은 Critic 값을 믿고 기본 행동을 바꾸지 않도록 막는다.
```

영어 원어가 필요하면 첫 설명 뒤에 괄호로 붙인다.

---

# 2. 설명 순서

핵심 개념 페이지는 가능한 한 다음 순서로 쓴다.

```text
왜 필요한가?
↓
쉬운 말로 무엇인가?
↓
작은 예를 보면 어떻게 동작하나?
↓
AASSR에서는 정확히 무엇을 하나?
↓
무엇과 헷갈리기 쉬운가?
↓
정확한 수학적 정의
↓
현재 코드 구현
↓
실험 방법
↓
확인된 실패 사례
↓
아직 증명하지 못한 것
```

수식이나 코드 식별자를 첫 설명보다 앞에 두지 않는 것을 기본으로 한다.

---

# 3. 영어 전문용어

## 처음 나올 때

한국어 설명을 먼저 쓴다.

예:

```text
희소 보상(sparse reward)
관계 기반 표현(relational representation)
학습 분포 밖(OOD, Out-of-Distribution)
```

가능하면 관련 상세 페이지 링크도 건다.

## 같은 페이지에서 다시 나올 때

이미 한 번 충분히 설명했다면 한국어 또는 익숙해진 고유 이름을 사용한다.

모든 반복 단어에 링크를 걸어 문장을 링크투성이로 만들 필요는 없다.

## AASSR 고유 모듈

다음 이름은 코드·연구에서 실제 고유 이름이므로 유지할 수 있다.

```text
Policy
Knowledge
Prophecy
Calibration
Critic
Imagination
ASEQ
Skills
```

다만 첫 등장에서는 역할을 같이 쓴다.

```text
Policy(기본 정책 모델)
Prophecy(미래 예측 모델)
Calibration(예측 신뢰도 보정)
Critic(미래 가치 평가기)
Imagination(가상 미래 탐색)
```

---

# 4. 코드 이름은 번역하지 않는다

실제 코드와 정확히 일치해야 하는 식별자는 그대로 쓴다.

```text
`current_manifest.py`
`build_current_pentest_aassr_core`
`critic_support_gate`
```

대신 주변 문장에서 뜻을 설명한다.

예:

```text
`current_manifest.py`는 현재 실제 실행 구조에서 어떤 구성요소가 활성화되어 있는지 기록한 최종 기준 파일이다.
```

---

# 5. 약어만 던지지 않는다

처음 등장하는 약어는 뜻을 풀어 쓴다.

```text
POMDP
→ 부분 관측 마르코프 의사결정 과정

OOD
→ 학습 분포 밖(Out-of-Distribution)

GRU
→ 과거 순서 정보를 내부 상태에 기억하는 순환 신경망 구조

TD
→ 다음 상태의 추정값을 이용해 현재 값을 학습하는 시간차 학습
```

---

# 6. 구현과 연구 증거를 구분한다

다음은 같은 뜻이 아니다.

```text
코드에 기능이 존재한다
≠
회귀 테스트에서 구조가 맞다
≠
진단 실험에서 메커니즘이 작동했다
≠
작은 실험에서 성능이 나왔다
≠
여러 난수 시드에서 비교 우위가 확인됐다
≠
최종 비공개 평가에서 확인됐다
```

따라서 문서에서 “검증됐다”라고 쓸 때는 **어느 수준의 증거인지** 같이 말한다.

관련: [연구 질문-증거 연결표](Evidence-Matrix)

---

# 7. 숫자만 던지지 않는다

예:

```text
24/24 → 0/24
```

만 쓰면 독자는 이 숫자가 무엇인지 알 수 없다.

다음처럼 설명한다.

```text
기본 정책에서 24개의 평가 문제 모두 제자리 반복으로 멈췄지만,
ASEQ의 반복 억제를 적용한 진단에서는 제자리 반복이 0개로 줄었다.

이 결과는 ASEQ의 제자리 반복 억제 메커니즘에 대한 증거다.
전체 AASSR 성공률이 항상 증가한다는 최종 성능 증거는 아니다.
```

---

# 8. 과거와 현재를 섞지 않는다

AASSR은 개발 과정의 실패 기록도 보존한다.

하지만:

```text
과거 진단 결과
```

를

```text
현재 모델의 성능
```

처럼 쓰면 안 된다.

현재 구조는 [현재 연구 상태](Current-Status)와 `src/aassr_v2/current_manifest.py`를 기준으로 한다.

과거 실패와 변경 과정은 [개발 역사](Development-History) 또는 별도 과거 진단 페이지에서 다룬다.

---

# 9. 문서가 길어져도 괜찮다

AASSR 위키는 API 요약 문서가 아니라 **연결된 연구 교과서**를 목표로 한다.

따라서 설명이 필요한데 단지 짧게 만들기 위해 생략하지 않는다.

대신 중복을 줄이기 위해 링크를 사용한다.

```text
현재 문장 이해에 필요한 설명
→ 현재 페이지에서 설명

더 깊은 일반 이론
→ 기초 개념 페이지 링크

현재 AASSR 구현
→ 구성요소 페이지 링크

실험 근거
→ Experiments / Evidence Matrix 링크
```

```markdown
## 현재 코드 구조

## 어떻게 학습하나?

## 어떤 실험으로 검증하나?

## 알려진 실패 사례

## 현재 증거로 말할 수 있는 것

## 관련 문서
```
