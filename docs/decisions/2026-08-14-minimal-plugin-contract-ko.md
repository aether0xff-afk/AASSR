# AASSR 최소 플러그인 계약 결정 기록

날짜: 2026-08-14
상태: 설계 원칙으로 고정
개정: 최소 권한 v2 — 후보 생성과 문제 해결 기억도 Core 소유로 강화

## 핵심 원칙

> **플러그인은 세계의 문법만 알려주고, 세계의 의미는 AASSR Core가 스스로 배운다.**

플러그인은 특정 환경을 AASSR에 연결하기 위한 얇은 입출력 계층이다. 플러그인이 문제의 의미를 해석하거나, 유망한 행동을 골라 주거나, 실패한 후보를 전략적으로 제거하거나, 이전에 발견한 문제 해결 지식을 대신 기억해서는 안 된다.

## 플러그인이 제공해도 되는 것

플러그인은 오직 다음 범위만 담당한다.

1. **행동의 종류와 형식**
   - 어떤 종류의 명령을 환경에 보낼 수 있는지
   - 행동에 필요한 매개변수와 자료형
   - Core가 고른 명령을 실제 환경 형식으로 직렬화하고 실행하는 방법

2. **관찰 정보의 종류와 형식**
   - 환경이 공개하는 관찰 채널의 종류
   - 각 관찰값의 자료형과 구조
   - 현재 실제 환경 응답을 손실 없이 AASSR에 전달하기 위한 형식 변환

3. **외부 신호의 전달**
   - 환경이 실제로 주는 보상
   - 종료 여부
   - 중단 여부
   - I/O 오류

4. **통신과 프로토콜 처리**
   - 네트워크, 로봇 제어, 게임 API 등 환경별 입출력 프로토콜 처리
   - 다음 명령을 실제로 수행하기 위해 필요한 프로토콜 상태
   - 예: 쿠키, 연결 세션, 통신 핸들

## 개정된 후보 행동 원칙

초기 기록에서는 Plugin이 "환경이 실행 가능한 행동 집합"을 제공해도 된다고 두었다. 구현 감사를 진행하면서 이 권한도 너무 넓다는 결론을 내렸다.

Plugin이 후보 목록을 만들면, 의도하지 않아도 다음이 가능해진다.

- 특정 후보를 빠뜨림
- 실패한 후보를 제거함
- 후보 순서를 통해 우선순위를 암시함
- 정답과 가까운 후보만 노출함

따라서 새 최소 계약에서는:

> **Plugin은 후보 행동 목록을 반환하지 않는다.**

Plugin은 `ActionSpec`과 매개변수의 자료형만 선언한다. Core가 자신이 실제로 관찰하고 기억한 typed value를 이용해 concrete command 후보를 만든다.

후보 수가 너무 많아 제한해야 할 때도 Core가 처리한다. concrete 이름의 사전순 앞부분을 자르는 방식은 이름 편향을 만들 수 있으므로 금지하고, Core가 seed 기반의 대칭적 bounded sampling을 담당한다.

## 관찰의 시간적 종류

Plugin은 관찰의 **의미**를 분류하는 대신 기계적인 수명만 선언할 수 있다.

- `STATE`: 현재 세계 상태의 일부로 지속되는 공개 값
- `EVENT`: 한 사건/응답에서 관찰된 공개 증거
- `COUNTER`: 누적 횟수
- `MEASUREMENT`: 매번 달라질 수 있는 측정값

Core는 `COUNTER`나 `MEASUREMENT`가 달라졌다는 이유만으로 semantic state가 달라졌다고 판단하지 않는다. 같은 `EVENT`가 반복된 것도 새로운 진전으로 세지 않는다. 이 규칙은 ASEQ의 정확한 `S → A → S` 의미를 지키기 위해 필요하다.

## 문제 해결 기억의 경계

Plugin이 보관해도 되는 것은 **실제 I/O를 수행하기 위한 프로토콜 상태**다.

예:

- 허용: HTTP CookieJar
- 허용: 열린 연결/session handle
- 금지: 이전 페이지에서 발견한 link 목록 누적
- 금지: 전에 실패한 후보 목록
- 금지: 어떤 대상이 유망해 보였는지 기록

이전에 무엇을 관찰했고 무엇을 시도했는가는 `CorePublicKnowledge`와 Core의 경험 기억이 담당한다.

Concrete 후보별 경험은 기본적으로 episode-local이다. 환경 reset 뒤 같은 문자열 ID가 다른 숨은 의미를 가질 수 있기 때문에, 그 경험을 자동으로 다음 episode에 넘기면 누수가 될 수 있다. 명시적으로 지식 보존 실험을 선택한 경우에만 보존한다.

## 플러그인이 해서는 안 되는 것

다음은 모두 AASSR Core의 책임이며 플러그인에 넣지 않는다.

- 어떤 관찰이 중요한지 판단하기
- 특정 행동이나 후보가 정답/오답이라고 해석하기
- 관계의 의미를 미리 부여하기
- 상태 벡터/semantic identity/행동 feature 정의
- 행동 우선순위를 정하기
- 후보 명령 집합을 전략적으로 구성하기
- 이미 관찰한 결과를 근거로 전략적 행동 필터링하기
- 탐색 순서를 정하기
- 실패 경험을 일반화하기
- world model/Prophecy 구현을 선택하거나 설치하기
- Critic/Imagination 점수를 정의하기
- 내부 보상 또는 shaping reward를 임의로 추가하기
- 숨은 정답 정보를 관찰값으로 바꾸어 노출하기
- 도메인 규칙을 이용해 Core 대신 추론하기

## Core가 반드시 담당하는 것

AASSR Core는 환경과 무관하게 다음을 스스로 수행해야 한다.

- 공개 typed value의 기억과 재사용
- concrete command 후보 생성
- bounded candidate sampling
- 의미 발견
- 관계 발견
- 지식 저장과 재사용
- 행동 가치 학습
- 탐색 전략
- 실패 학습과 일반화
- Policy
- Knowledge
- Prophecy
- Critic
- Imagination
- ASEQ
- Skills
- Calibration 및 신뢰도 판단

Core는 특정 환경의 도메인 용어를 알 필요가 없어야 한다.

## 설계 판정 기준

새 기능을 추가할 때 다음 질문을 적용한다.

> **이 기능이 없으면 환경과 통신 자체를 할 수 없는가, 아니면 문제를 더 잘 풀 수 없게 되는가?**

- 환경과 통신 자체가 불가능 → Plugin 후보
- 문제 해결 능력이 떨어짐 → Core가 학습할 책임

그리고:

> **이 코드가 데이터의 형식/수명만 설명하는가, 아니면 관찰의 의미를 해석하는가?**

- 형식/수명 설명 → Plugin 허용
- 의미 해석/전략 판단 → Core 책임

## 기존 pentest 구조에 대한 영향

기존 `current_*`와 `plugins/current_pentest.py`는 10k 체크포인트와 과거 실험을 재현하기 위해 유지한다. 그러나 새 Plugin 제작 기준으로 사용하지 않는다.

기존 simulator는 폐기하지 않지만 앞으로는 주로 다음 용도로 사용한다.

- 단위 테스트
- 회귀 테스트
- ASEQ/self-loop 검증
- checkpoint/학습 계약 검증
- 고장 주입과 작은 메커니즘 검증

AASSR의 실제 일반성 검증은 새 Core를 먼저 단단히 한 뒤 최소 Plugin을 통해 로컬의 실제 환경과 연결하는 방향을 우선한다.

## 금지되는 성공 방식

Plugin에 도메인 지식을 추가해 성공률을 높이는 것은 AASSR Core의 성능 향상으로 간주하지 않는다.

AASSR이 실제 경험으로 의미와 관계를 발견해 성능을 높였을 때만 Core의 능력 향상으로 인정한다.
