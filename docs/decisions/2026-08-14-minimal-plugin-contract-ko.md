# AASSR 최소 플러그인 계약 결정 기록

날짜: 2026-08-14
상태: 설계 원칙으로 고정

## 핵심 원칙

> **플러그인은 세계의 문법만 알려주고, 세계의 의미는 AASSR Core가 스스로 배운다.**

플러그인은 특정 환경을 AASSR에 연결하기 위한 얇은 입출력 계층이다. 플러그인이 문제의 의미를 해석하거나, 유망한 행동을 골라 주거나, 실패한 후보를 전략적으로 제거해서는 안 된다.

## 플러그인이 제공해도 되는 것

플러그인은 오직 다음 범위만 담당한다.

1. **행동의 종류와 형식**
   - 어떤 종류의 행동을 환경에 보낼 수 있는지
   - 행동에 필요한 매개변수와 자료형
   - 행동을 실제 환경 형식으로 직렬화하고 실행하는 방법

2. **관찰 정보의 종류와 형식**
   - 환경이 공개하는 관찰 채널의 종류
   - 각 관찰값의 자료형과 구조
   - 실제 환경 응답을 손실 없이 AASSR에 전달하기 위한 형식 변환

3. **환경이 실제로 허용하는 행동 집합**
   - 전략적으로 좋은 행동만 남기는 필터가 아니라, 현재 환경에서 실행 가능한 행동만 제공

4. **외부 신호의 전달**
   - 환경이 실제로 주는 보상
   - 종료 여부
   - 실패/중단 등 환경의 공개 종료 신호

5. **통신과 프로토콜 처리**
   - HTTP, 로봇 제어, 게임 API 등 환경별 입출력 프로토콜 처리

## 플러그인이 해서는 안 되는 것

다음은 모두 AASSR Core의 책임이며 플러그인에 넣지 않는다.

- 어떤 관찰이 중요한지 판단하기
- 특정 행동이나 후보가 정답/오답이라고 해석하기
- 관계의 의미를 미리 부여하기
- 행동 우선순위를 정하기
- 이미 관찰한 결과를 근거로 전략적 행동 필터링하기
- 탐색 순서를 정하기
- 실패 경험을 일반화하기
- 내부 보상 또는 shaping reward를 임의로 추가하기
- target, 정답 route, 정답 profile 등 숨은 정답 정보를 노출하기
- 도메인 규칙을 이용해 Core 대신 추론하기

예를 들어 pentest 환경에서 플러그인이 `request_profile_not_applicable` 같은 공개 응답을 전달하는 것은 허용된다. 그러나 플러그인이 그 응답을 보고 "이 profile은 앞으로 제거"라고 결정하는 것은 허용하지 않는다. 그 의미를 기억하고 재사용할지는 AASSR Core가 학습해야 한다.

## Core가 반드시 담당하는 것

AASSR Core는 환경과 무관하게 다음을 스스로 수행해야 한다.

- 의미 발견
- 관계 발견
- 지식 저장과 재사용
- 행동 가치 학습
- 탐색 전략
- 실패 학습과 일반화
- Policy
- Knowledge
- Prophecy
- Critic
- Imagination
- ASEQ
- Skills
- Calibration 및 신뢰도 판단

Core는 `HTTP`, `route`, `profile`, `CSRF`, 특정 게임 오브젝트 같은 도메인 용어를 알 필요가 없어야 한다.

## 설계 판정 기준

새 기능을 추가할 때 다음 질문으로 Core/Plugin 위치를 결정한다.

> **환경을 다른 문제로 바꿔도 이 판단이 그대로 필요한가?**

- 그렇다 → Core 후보
- 아니다 → Plugin 또는 환경 계층 후보

그리고 다음 질문을 한 번 더 적용한다.

> **이 코드가 단순히 입출력 형식을 설명하는가, 아니면 관찰의 의미를 해석해 행동을 더 잘 고르게 해 주는가?**

- 입출력 형식 설명 → Plugin 허용
- 의미 해석/전략 판단 → Core가 학습해야 함

## 현재 pentest 구조에 대한 영향

기존 pentest simulator와 plugin은 이 원칙을 기준으로 다시 감사한다. 특히 plugin이 route/profile/object의 의미 역할, 상태 의미, 행동 우선순위, 도메인별 전략 필터를 지나치게 제공하는 부분이 있는지 확인한다.

기존 simulator는 폐기하지 않지만 앞으로는 주로 다음 용도로 사용한다.

- 단위 테스트
- 회귀 테스트
- ASEQ/self-loop 검증
- checkpoint/학습 계약 검증
- 고장 주입과 작은 메커니즘 검증

AASSR의 실제 일반성 검증은 Core를 먼저 단단히 한 뒤, 최소 플러그인을 통해 로컬의 실제 환경과 연결하는 방향을 우선한다.

## 금지되는 성공 방식

플러그인에 도메인 지식을 추가해 성공률을 높이는 것은 AASSR Core의 성능 향상으로 간주하지 않는다.

AASSR이 경험으로 의미와 관계를 발견해 성능을 높였을 때만 Core의 능력 향상으로 인정한다.
